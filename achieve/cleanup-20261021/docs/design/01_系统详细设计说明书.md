# 统一权限管理系统——系统详细设计说明书
## 1. 设计目标与边界

| 项目 | 约束 |
|---|---|
| 系统职责 | 统一账号、统一登录、菜单权限管理、后端 API 鉴权及管理员后台；本系统自身也纳入权限管理 |
| 外部边界 | HR 是正式及外包员工人事数据唯一来源；OA 负责审批；业务系统使用本系统的认证、菜单及鉴权接口 |
| 权限模型 | 第一阶段严格 RBAC0：用户—角色—菜单权限；只有允许，多角色取并集；菜单关联后端 API |
| 不在本期实现 | 角色继承、角色先决约束、显式禁止、权限自动过期、RBAC3 职责分离 |
| 分级管理 | 总公司及各级部门管理员按等级、部门管理范围开展操作；应用本身不设分公司使用限制 |
| 实时性与性能 | 有效权限被撤销后，下一次相关 API 请求不得错误放行；鉴权目标不超过 20ms、上限 50ms；约一万人集中登录场景 |
| 安全审计 | 姓名、手机号加密保护；手机号和权限数据非对称签名；验签失败不能授权；日志永久保留；每周全量、每日增量备份，人工恢复 |
| 实现约束 | 结构化设计方法；Java + Spring Boot；基于现有 MySQL 8 数据库协同完善 |

**设计原则**：权限判断必须在后端实施，失败默认拒绝；当前有效状态不从 JWT 中推断；功能授权、管理员对象范围和 HR/OA 业务流程分离；可恢复性和证据保全优先于故障时继续放行。

**与需求的偏差记录**：需求规定重名用户名"拼手机号后几位"，本设计改用追加 SG 号后六位。原因：手机号属隐私数据且加密存储，把明文手机号片段写入用户名会部分泄露手机号，并使用户名规则依赖密文数据；SG 号是 HR 人员稳定标识，重名消歧的确定性更强。除此之外，本设计不偏离需求的其他硬性规定（登录方式仅账号密码、手机号密码两种，不含短信验证码登录）。

## 2. 六模块分解与协作

![alt text](统一权限管理系统功能架构图-1.png)

| 模块 | 子功能范围 | 主要负责 | 明确不负责 |
|---|---|---|---|
| **M1 身份认证与账号管理** | 1.1—1.5 | 账号生成、临时账号、账号状态、两种密码登录、JWT 会话 | HR 变动编排、角色授权 |
| **M2 组织与人员变动管理** | 2.1—2.6 | 组织树、HR 接入、调岗、离职、合并、部门冻结流程 | 重复实现 M1 账号算法或 M4 授权写入 |
| **M3 应用权限资源管理** | 3.1—3.5 | 应用、菜单、API、菜单—API 关联及资源有效性 | 计算用户当前权限 |
| **M4 角色与授权管理** | 4.1—4.5 | 角色、角色菜单、用户角色、批量授权及 OA 审批结果执行 | OA 审批、在线请求鉴权 |
| **M5 管理员与管理范围控制** | 5.1—5.6 | 任命撤销、等级、范围、管理操作合法性、超级用户兜底 | RBAC1 角色继承、直接授予普通用户菜单 |
| **M6 在线权限鉴定** | 6.1—6.6 | 当前身份与状态、菜单并集、API 判定、实时撤权与可信缓存 | 修改用户—角色、角色—菜单关系 |

**公共支撑处理**不计入六模块：敏感数据保护、数字签名与验签、操作审计、备份及人工恢复；缓存基础设施由公共技术设施提供，业务一致性规则归 M6 协调。

**核心协作规则**：

1. **HR 变动**：M2 验证事件并编排；账号信息由 M1 处理，用户角色关系由 M4 处理，涉及有效权限的变化由 M6 协调可信状态更新。
2. **管理后台授权**：M6 验证操作功能权限，M5 校验有效管理员身份、目标范围及操作级别，M4 才执行授权；**两个检查必须同时通过**。
3. **业务资源变更**：M3 修改应用/菜单/API/映射，先协调 M6 的受影响范围保护，再提交和发布新可信状态。
4. **在线鉴权**：业务系统服务端携带可信调用方身份、用户 JWT 和实际目标 API，M6 返回允许/拒绝；实际业务后端必须执行该结果。

| D2 | `sys_dept` | M2 |
| D3 | `sys_application`、`sys_menu`、`sys_api`、`sys_menu_api` | M3 |

|---|---|

权限状态变更|	M1—M5 中影响权限的业务操作 → M6 协调变更保护、可信权限状态与缓存更新 → 新权限状态可用于后续鉴权；异常时安全拒绝

## 3. M1 身份认证与账号管理

负责统一账号的创建与维护、账号状态管理、身份认证、密码管理及 JWT 会话管理。正式员工和外包员工账号由 M2 协调 HR 同步生成，临时账号由管理员创建。M1 不负责角色授权和业务权限计算，后者分别由 M4、M6 处理。

### 3.1 账号生成与维护（1.1）

- **输入**：M2 已验证的 HR 人员 SG 标识、姓名、手机号、部门、人员类型及事件标识。正式员工和外包员工账号仅通过 HR 同步创建，不允许管理员手工创建。

- **处理**：以 SG 号作为员工稳定人员标识，优先查询已有账号；核对手机号及人员唯一性，保证一人一账号。新账号以姓名拼音首字母生成用户名；发生重名时，追加该员工 SG 号的后六位。用户名创建后保持不变，人员信息变化时更新原账号，不重复创建。最终通过数据库唯一约束防止并发重复创建。

- **首次使用**：HR 同步创建账号后，员工通过预留手机号接收短信验证码完成身份验证并设置登录密码。未设置密码的账号不能登录；短信验证码仅用于验证本人身份以支持首次设密和密码重置，不作为登录方式（见 3.4 节）。

- **存储**：姓名和手机号加密保存，手机号 HMAC 索引用于唯一查询，密码仅保存带盐单向哈希，关键身份数据使用非对称数字签名保护。数据校验失败或唯一性冲突时不自动合并人员。

- **异常处理**：SG 号重复且人员资料冲突、手机号已绑定其他账号、用户名生成冲突等情况应拒绝自动处理，保留异常记录并交由人工核查。

### 3.2 临时账号管理（1.2）

- **创建**：管理员通过 M6 功能权限检查和 M5 管理范围检查后，为无工号外部人员创建临时账号。必须提供姓名、有效且未被其他账号绑定的手机号、所属部门和使用原因，并记录创建人。
- **账号属性**：临时账号即手动创建的普通账号，不设独立账号类型，仅以 `source=2`、`employee_no=NULL` 并记录创建人及用途区分；禁止通过该接口创建带工号的正式或外包员工账号（有工号的账号只能由 HR 同步生成）。
- **首次使用**：临时人员通过绑定手机号接收短信验证码完成首次身份验证并设置登录密码，设密后方可登录。登录规则与普通员工一致。
- **维护与停用**：手动创建（`source=2`）的账号可由授权管理员在权限范围内查询、暂停及恢复。停用使用现有“暂停”状态，不增加新的账号状态；停用后禁止登录和使用业务权限。账号及历史记录保留，不物理删除。
- **权限规则**：临时账号通过 M4 分配角色，权限由 M6 按 RBAC0 计算，不因临时账号身份自动获得业务权限。本期不设置角色权限自动到期机制。

### 3.3 账号状态管理（1.3）

系统保留可用、暂停、离职三种账号状态。密码是否已初始化通过独立凭据状态管理。

| 状态变化 | 处理规则 |
|---|---|
| 可用 → 暂停 | 禁止登录及业务访问，保留账号和角色记录；手动创建（`source=2`）的账号可由授权管理员暂停及恢复，HR 同步账号的状态由 HR 事件驱动，不开放人工暂停 |
| 暂停 → 可用 | 经合法操作恢复，重新启用仍然有效的原有权限，不自动新增角色 |
| 可用/暂停 → 离职 | 仅由可信 HR 离职事件触发；保留账号及历史记录，未过期 JWT 也不能继续鉴权 |
| 任意状态 → 物理删除 | 禁止 |

**部门冻结与账号状态相互独立**：

- 部门冻结不修改用户的账号状态，也不撤销其原有角色关系。
- 冻结部门及下属部门的可用账号仍允许登录、注销和进行必要的密码安全操作（设计决定：冻结作用于业务权限鉴定，不阻断认证通道，保证员工冻结期间仍可维护凭据；受保护业务权限一律拒绝）。
- M6 在菜单查询和受保护业务 API 鉴权时检查部门及祖先部门冻结状态，禁止使用业务权限。
- 解除冻结后，重新按当前账号、角色及资源状态计算有效权限，不自动新增授权。

账号状态及其他影响权限的变更须通知 M6 更新可信鉴权状态，确保变更生效后不继续使用过期授权。

### 3.4 身份凭据校验（1.4）

系统支持两种登录方式，均为密码登录：

1. **账号密码登录**：用户输入用户名及密码。系统根据唯一用户名查询账号，验证已初始化的密码哈希。
2. **手机号密码登录**：用户输入绑定手机号及密码。系统根据规范化手机号的 HMAC 索引查询账号，验证已初始化的密码哈希。

**短信验证码不是登录方式**：短信验证码仅用于验证本人身份，支持首次设置密码和密码重置两个场景，不提供免密登录。未设置密码的账号不能登录，须先通过短信验证码完成身份验证并设置密码（见 3.1、3.5 节）。

**统一校验规则**：

- 两种方式均检查账号状态及必要身份数据的数字签名；账号暂停、离职、未完成首次设密或关键身份数据验签失败时拒绝登录。
- 部门冻结不阻止登录，但冻结范围内的用户无法使用受保护业务权限。
- 验证码按首次设密、密码重置区分用途，设置有效期、发送频率和验证次数限制；验证成功后立即失效，不得重复或跨用途使用。
- 登录失败统一返回安全提示，实施适度限流，记录成功及失败日志，不泄露账号是否存在、完整手机号、密码或验证码。
- 认证成功后交由 M1 登录会话处理签发 JWT，不直接授予角色或菜单权限。

### 3.5 登录会话管理（1.5）

**1. JWT 会话管理**

- 登录成功后签发带有效期的 JWT，允许受信任的接入业务系统通用。
- JWT 建议包含 `sub`、`iss`、`aud`、`iat`、`exp`、`jti` 等身份及会话字段，不将角色和菜单列表作为固定权限写入令牌。
- 验证 JWT 时检查签名、签发方、受众、有效期及注销状态。JWT 有效不代表拥有业务权限，每次受保护 API 请求仍须由 M6 检查当前权限。
- 用户注销时通过共享令牌失效记录或会话版本机制，使对应 JWT 立即失效。
- 部门冻结不主动注销用户会话，但 M6 必须禁止被冻结用户使用业务权限。

**2. 密码设置与重置**

- **首次设置密码**：用户通过绑定手机号的专用验证码验证身份后，设置符合 9.1 节密码策略的密码。系统保存带盐密码哈希并更新密码初始化状态。
- **忘记密码**：用户使用手机号及密码重置专用验证码完成身份验证，再设置新密码，不要求提供旧密码。
- **重置成功**：原密码失效，同时撤销该账号原有登录会话，用户须重新认证。
- **异常处理**：验证码错误、过期或超过尝试次数时拒绝操作；密码更新失败时不得覆盖原密码。全过程记录安全审计日志，不记录明文密码或验证码。

**3. 会话安全**

登录及密码管理接口须采用加密传输，限制异常请求频率。JWT 不存储密码、手机号等敏感信息。会话注销、账号停用和密码重置后的失效状态须能被 M6 及时识别，避免旧令牌继续获得访问权限。

## 4. M2 组织与人员变动管理

负责组织结构维护、HR 数据同步，以及调岗、离职、部门合并和部门权限冻结等业务处理。HR 是正式员工、外包员工及组织数据的权威来源。

M2 负责业务流程协调和组织数据维护；账号变更由 M1 执行，角色授权与回收由 M4 执行，管理员范围由 M5 检查，权限变更后的实时生效由 M6 保障。

### 4.1 组织结构维护（2.1）

- **数据结构**：使用 `sys_dept.id` 作为部门唯一标识，`parent_id` 和 `dept_path` 维护组织树。部门名称可能重复，不作为唯一识别依据。
- **组织更新**：根据可信 HR 数据执行部门新增、修改、层级调整及合并。操作前校验部门 ID、父节点有效性及组织关系，禁止形成循环；操作后同步更新受影响子树的路径。
- **人员归属**：员工通过 `sys_user.dept_id` 关联部门。组织调整时按部门 ID 更新归属，不能仅凭部门名称匹配；部门经理须关联明确的用户 ID，不能仅根据姓名推断。
- **管理范围**：组织关系变化后通知 M5 重新校验受影响管理员的管理范围。若原管理根部门失效，暂停相应管理操作，等待重新任命，不自动扩大管理权限。
- **异常处理**：部门 ID 不存在、父子关系无效、出现组织环或数据冲突时拒绝更新，记录异常并交由人工核查。

HR 与本系统交换部门数据时，必须保证事件中的部门标识能够正确对应 `sys_dept.id`；无法对应时不根据名称猜测。

### 4.2 HR 数据同步（2.2）

**输入**：可信 HR 系统发送的统一格式事件，包含来源系统、唯一事件 ID、事件类型、变更版本、发生时间及业务数据。人员事件使用 SG 号作为稳定人员标识，组织事件使用明确的部门 ID。

**服务身份约束**：HR 服务身份绑定受控操作范围，仅允许人员与组织事件类型，不得作为角色授权、管理员任命或其他管理操作的写入入口；HR 事件不携带也不产生角色授权。

**处理步骤**：

1. 验证 HR 调用方身份及事件数据完整性。
2. 根据来源系统和事件 ID 进行幂等检查：同一事件及相同内容返回已有结果，不重复执行；同一事件 ID 对应不同内容时返回冲突。
3. 按人员或部门的变更版本检查事件顺序。旧版本事件不得覆盖新版本数据。
4. 根据事件类型分派入职、信息更新、调岗、离职或组织变更处理。
5. 协调相关模块执行业务更新，同时完成必要的数据签名、审计和可信权限状态更新。
6. 保存处理状态与执行结果，供 HR 重试查询。

**异常处理**：事件乱序、部门不存在、数据冲突或处理失败时，不执行不安全的后续操作；保留异常记录，支持受控重试或人工处理。

**数据支持**：增加统一的外部事件处理记录，以 `(source_system, event_id)` 唯一约束保证原子幂等，保存事件摘要、业务版本、处理状态及执行结果；数据库设计 v3.0 已以 `sys_external_event` 表落实。

### 4.3 调岗处理（2.3）

**业务规则**：有效调岗事件到达后，立即启动旧岗位权限回收；完成旧权限处理后更新部门归属，新部门角色由管理员人工分配，不根据岗位变化自动授权。

**处理步骤**：

1. **接收与校验**：M2 验证 HR 调岗事件、员工 SG 号、原部门、新部门及事件版本，确认事件有效且未重复处理。
2. **限制旧权限**：事件通过校验后，立即协调 M6 对受影响用户设置临时鉴权限制，防止调岗过程中继续使用待回收的旧岗位权限。
3. **识别授权来源**：查询该用户每项角色授权的业务来源，找出因原部门或原岗位取得、需要随调岗撤销的授权依据。
4. **回收旧授权**：M4 撤销对应授权依据。如果同一用户—角色关系仍有其他合法授权依据，则保留该角色；仅当所有有效依据均不存在时，才撤销用户—角色有效关系。
5. **更新部门归属**：确认旧岗位授权已完成回收后，由 M2 更新组织关系、M1 更新员工所属部门，并重新检查部门冻结及管理员管理范围。
6. **更新鉴权状态**：M6 根据最新账号、组织和授权数据发布可信权限状态，解除不再需要的临时限制。记录旧权限回收及部门变更的完成结果。
7. **新岗位授权**：新部门管理员经 M6 功能权限及 M5 管理范围校验后，由 M4 人工分配新岗位角色。新授权再次更新可信权限状态。

**授权来源规则**：

- 每项用户—角色分配必须记录授权类型、来源部门或岗位、业务依据及关联事件。
- `granted_by` 仅表示授权操作人，不能作为岗位授权来源。
- 同一用户可以因不同业务依据获得同一角色。撤销其中一项依据时，不影响其他仍然有效的授权。

**失败处理**：

- 无法确定旧岗位授权来源时，不自动删除不明来源的角色关系；保留受影响用户的安全限制，并生成人工核查任务。
- 任一阶段失败时，保存已完成阶段、失败原因和待处理事项，不报告整个调岗已完成。
- 对已提交的变更不假定可以跨事务整体回滚；恢复处理应以实际数据库状态为依据。
- 旧权限回收和组织更新完成后，可记录为“待新部门授权”；新岗位授权作为后续人工操作，不得因其尚未完成而恢复旧岗位权限。

**数据库适配**：`sys_user_role_source` 表达同一用户—角色的多个独立授权依据（来源类型、来源标识、来源部门、状态）；`sys_user_role` 仅在至少存在一个有效依据时保持有效。授权变更和来源记录保持事务一致。

### 4.4 离职处理（2.4）

- **输入**：可信 HR 离职事件，包含员工 SG 号、事件 ID 及变更版本。
- **处理**：M2 验证事件后，协调 M1 将账号状态更新为离职，并通知 M6 立即停止该账号的业务访问。
- **历史保留**：保留用户账号、历史授权依据及操作日志，不物理删除历史记录。离职后即使 JWT 尚未过期，M6 仍必须拒绝受保护业务请求。
- **复职处理**：复职或再次入职必须由新的可信 HR 事件触发；同一 SG 号沿用原人员账号，但不得自动恢复离职前的有效岗位权限。旧授权须重新审核后由 M4 恢复或重新分配。
- **异常处理**：SG 号不存在、事件重复冲突或版本错误时不直接修改账号状态；处理失败则保持相应安全限制并记录异常。

### 4.5 部门合并处理（2.5）

- **组织更新**：根据可信 HR 合并事件，调整部门层级、员工所属部门和组织路径，校验合并目标、父子关系及受影响子树的一致性。
- **权限处理**：合并时暂时保留员工已有的用户—角色关系，不自动回收旧角色，也不因合并自动授予新角色；正常情况下，原有合法业务权限仍可使用。
- **后续调整**：由新部门管理员在其管理范围内人工检查并调整相关岗位角色，保留处理记录。
- **管理员范围**：若合并导致原管理员管理根部门失效，则立即限制其受影响管理操作，并由具备任命资格的管理员重新确定管理范围，不自动迁移到更大的部门。
- **冻结关系**：重新计算员工及部门的冻结祖先链。HR 组织合并不自动解除原有冻结状态；因迁入被冻结的组织范围而受到冻结限制的用户，应立即停止使用业务权限。
- **异常处理**：组织更新或可信状态发布失败时保留受影响范围的安全限制，记录阶段结果并进入受控恢复，不直接报告合并完成。

### 4.6 部门权限冻结与解除（2.6）

**操作权限**：冻结或解除冻结请求须通过 M6 的管理功能权限检查，以及 M5 的管理员资格和目标部门范围检查。

**冻结处理**：

1. 校验目标部门及操作者管理范围。
2. 将目标部门设置为冻结状态，保留原有员工账号和用户—角色关系。
3. M6 检查用户所在部门到组织根节点的冻结状态，任一祖先被冻结时，均拒绝该用户使用受保护的业务权限。
4. 更新可信鉴权状态，确保冻结生效后不再使用过期的允许结果。
5. 记录操作人、目标部门、影响范围及执行结果，完成签名和审计。

**解除冻结**：

- 经合法授权后解除目标部门的冻结标记。
- 若上级部门仍被冻结，该部门员工的业务权限继续不可用。
- 全部相关冻结解除后，仅恢复当前账号、角色及资源状态下原本有效的权限，不自动新增授权。

**冻结与登录的关系**：

- 部门冻结不改变账号状态，不阻止用户登录、注销及必要的密码安全操作（设计决定：冻结针对业务权限，不阻断认证通道，避免冻结期间员工无法自助维护凭据）。
- 被冻结部门及其下属部门的用户，菜单查询不返回可操作的业务菜单，受保护业务 API 鉴权一律拒绝。
- 部门冻结不通过 RBAC0 显式拒绝权限实现，而是作为 M6 的独立业务状态约束。

**恢复管理**：被冻结部门的普通管理员不能借登录权限绕过业务权限冻结；解冻操作应由未受该冻结限制且具有相应权限的上级管理员执行。超级用户恢复通道由 M5 单独受控，所有恢复操作必须记录审计，不能绕过数据签名校验。

### 4.7 关键数据与模块协作

| 数据或处理 | 责任模块 | 设计要求 |
|---|---|---|
| 部门主键、组织树、冻结状态 | M2 | `sys_dept.id` 唯一识别部门 |
| 员工 SG 标识、账号状态和部门归属 | M1 | M2 根据 HR 事件协调更新 |
| 用户—角色授权及业务来源 | M4 | 支持同一用户角色存在多个独立授权依据 |
| 管理员等级、任命和管理范围 | M5 | 组织变化后重新校验，不自动扩大范围 |
| 实时权限限制及可信状态更新 | M6 | 撤权、冻结、离职后立即使用最新有效状态 |
| HR 事件幂等及调岗阶段记录 | M2 | 唯一事件号、版本校验、失败可追溯 |
| 数字签名、审计 | 公共支撑 | 关键业务变更必须保留可信证据 |

## 5. M3 应用权限资源管理

负责应用、菜单、API 资源及菜单—API 关联关系的登记、维护和有效性校验，为 M4 角色授权和 M6 在线鉴权提供可信资源数据。

**管理权限**：全局资源由具有对应管理功能权限的一级总公司管理员维护。操作时须通过 M6 功能权限校验和 M5 一级管理员资格校验，二级及以下管理员不得修改全局资源。超级用户保留受控的初始化和紧急恢复能力。

### 5.1 应用系统管理（3.1）

- **资源登记**：维护应用编号 `app_code`、名称、描述和启停状态，包含统一权限管理系统自身及接入的业务系统。至少配置两个演示业务系统，每个设置 3—4 个菜单。
- **使用范围**：应用不按分公司或部门划分使用范围。用户能否访问应用功能取决于实际获得的菜单权限。
- **启停管理**：应用停用后，其所有菜单不再提供有效授权，该应用的受保护 API 一律拒绝访问；原有资源和授权关系保留，重新启用后按当前有效权限计算。
- **自身保护**：统一权限管理系统自身的应用记录禁止停用，防止管理入口整体失效后无法恢复；该保护由服务层强制执行，不依赖前端隐藏入口。若因数据事故被误停用，按 9.4 节人工恢复流程处理。
- **变更处理**：应用新增、修改和启停均须验证管理权限、资源唯一性及数据完整性，并通知 M6 更新可信鉴权状态。

### 5.2 菜单资源管理（3.2）

- **菜单分类**：`menu_type=1` 为导航目录，不可直接授权；`menu_type=2` 为权限菜单，可通过 M4 授予角色。目录层级仅用于组织和展示，不产生 RBAC0 角色权限继承。
- **层级维护**：新增或移动菜单时，检查父节点存在、属于同一应用，且不会形成循环。菜单移动仅调整导航位置，原有角色—菜单授权关系保留。
- **停用规则**：停用上级导航目录时，其全部下级菜单及通过这些菜单获得的 API 权限立即失效。系统通过检查菜单祖先目录状态实现级联失效，不必删除或改写下级菜单及历史授权记录。
- **恢复规则**：重新启用上级目录后，下级菜单根据自身状态、其他祖先状态和现有角色授权重新计算有效性，不自动新增授权。
- **菜单查询**：M6 仅返回当前有效的授权菜单，可补全必要的祖先目录用于页面展示；补全的目录不产生额外 API 权限。
- **移动影响**：菜单移动后按照新的祖先目录状态重新判定是否有效，并及时更新受影响的可信鉴权状态。

### 5.3 API 资源管理（3.3）

- **资源登记**：维护受保护 API 的所属应用、HTTP 请求方法、路由模板、描述及启停状态，以 `(app_id, http_method, api_path)` 唯一标识 API。
- **登记校验**：接入业务系统提供实际后端 API 路由模板，如 `/users/{id}`。M3 对请求方法、路径格式及路由模板进行规范化和冲突检查，禁止重复、歧义或跨应用错误登记。
- **资源维护**：具有对应管理功能权限的一级总公司管理员可新增、修改及停用 API。停用后保留资源及历史关联记录，不作为当前有效权限资源。
- **变更通知**：API 登记、修改及启停后，通知 M6 更新对应的可信资源状态，确保后续鉴权使用最新资源数据。


### 5.4 菜单—API 关联管理（3.4）

- **关联规则**：同一应用内的权限菜单与 API 支持多对多关联。一个菜单可关联多个 API，一个 API 也可被多个权限菜单关联。
- **权限判定**：用户只要拥有某个 API 所关联的任一有效权限菜单，即满足该 API 的菜单授权条件；最终是否允许访问仍由 M6 检查账号、部门、应用和 API 等状态。
- **关联限制**：只有 `menu_type=2` 的权限菜单可以绑定 API；目录菜单不得绑定 API，不允许跨应用关联。
- **目录停用影响**：被停用目录下的菜单不再提供 API 授权。如果某 API 同时关联其他仍然有效的菜单，则仍可依据其他菜单完成授权判定。
- **关联变更**：新增、删除或修改映射均须校验管理权限和数据完整性，并更新 M6 可信权限状态，避免旧关联继续产生权限。

### 5.5 资源有效性校验（3.5）

M3 提供统一的资源有效性校验规则，M6 在在线鉴权时依据当前可信资源状态执行判定。

**有效权限菜单必须同时满足**：

1. 所属应用处于启用状态。
2. 菜单自身处于启用状态，且类型为权限菜单。
3. 菜单的全部祖先导航目录均处于启用状态。
4. 菜单及关联数据的签名、版本可信。

**API 获得有效授权必须同时满足**：

1. API 及所属应用处于启用状态。
2. 请求来自对应应用的可信业务服务，且实际路由匹配已登记 API。
3. 用户至少具有一个与该 API 有效关联的权限菜单。
4. 相关资源及授权数据通过完整性与版本检查。

已停用的应用、目录、菜单及 API 可以在管理界面查询和审计，但不能作为有效授权依据。资源变更完成后，M6 必须使用最新可信状态进行后续鉴权。

## 6. M4 角色与授权管理

负责角色维护、角色—菜单授权、用户—角色授权、批量授权及 OA 审批结果执行。采用 RBAC0 模型，用户可以拥有多个角色，角色权限取并集，不实现角色继承。

M4 负责维护授权关系，不负责在线 API 鉴权；管理操作须通过 M6 功能权限检查及 M5 相应的管理资格与范围检查，授权变更由 M6 协调实时生效。

### 6.1 角色管理（4.1）

- **角色创建与维护**：按岗位及业务职责建立可复用角色，维护角色名称、类型、描述及启停状态。`role_type` 用于区分业务、管理及超级角色，本身不产生权限。
- **管理权限**：只有具有对应角色管理功能权限的一级总公司管理员可以创建、修改和停用普通业务角色及管理角色。二级及以下管理员不能修改全局角色定义，但可以使用上级允许其授予的已有角色。
- **角色停用**：停用角色后，其权限不再生效，但保留已有用户—角色关系及历史授权证据；重新启用后按当前有效授权重新计算。
- **超级角色**：超级角色的创建及维护仅通过受控初始化和恢复流程进行，不允许普通管理员通过角色管理接口创建或修改。
- **变更处理**：角色变更须进行合法性、签名和并发检查，记录审计，并通知 M6 更新可信权限状态。

### 6.2 角色菜单授权（4.2）

- **授权内容**：维护 `sys_role_permission`，将权限菜单（`menu_type=2`）分配给角色。一个角色可以拥有多个应用的菜单，导航目录不能直接授权。
- **修改权限**：只有具有对应角色菜单管理功能权限的一级总公司管理员可以增加、删除或调整角色拥有的菜单。二级及以下管理员不得修改角色—菜单关系。
- **权限影响**：修改角色菜单可能同时影响所有持有该角色的用户，因此变更后必须更新受影响的可信权限状态。已停用菜单及其冻结的祖先目录不参与有效授权。
- **并发控制**：角色菜单集合修改采用版本比较或等效并发保护，版本冲突时拒绝提交，不覆盖其他管理员已经完成的修改。
- **历史记录**：保留角色菜单变更的操作人、变更前后内容及审计记录。

### 6.3 用户角色授权与回收（4.3）

**1. 可授权角色范围**

- 一级总公司管理员在具有相应功能权限的前提下，可以管理集团范围内的普通业务角色及符合等级规则的管理角色授权。
- 二级及以下管理员只能向其管理范围内的用户授予或回收上级明确允许的角色。
- 上级管理员负责配置下级管理员的**可授权角色清单**，清单中的角色必须属于上级自身有资格委派的角色范围，不能通过逐级委派扩大权限。
- `role_type` 作为基础安全限制：普通授权接口禁止分配超级角色；管理角色的分配还须符合管理员等级及任命规则。
- 角色分配不自动产生管理员任命。即使用户拥有管理功能角色，仍须具有有效 M5 管理员资格才能执行管理操作。

**2. 授权操作**

- 管理员发起用户角色授权时，M6 检查其是否拥有用户角色授权功能权限，M5 检查有效管理员资格、目标用户所属管理范围及拟授予角色是否在可授权清单内。
- 所有检查通过后，由 M4 建立或更新用户—角色授权关系，并记录授权业务来源。
- 同一用户可拥有多个角色，角色之间不继承权限；当前有效菜单由各有效角色的菜单集合取并集。
- **允许管理员为自己分配可授权清单内的角色**，但必须通过与授权其他用户相同的功能权限、管理范围和角色资格检查，不得借此取得超出既有授权资格的角色。

**3. 角色回收**

- 管理员可以回收其有权管理的用户角色，也可以回收自己有权管理的角色，均须通过完整的功能权限、管理范围和角色资格校验。
- 每项用户—角色授权须记录实际业务来源。回收某项授权依据时，若该用户对同一角色仍存在其他合法授权依据，则保留该角色的有效授权；只有不存在其他有效依据时，才使用户—角色关系失效。
- 回收一个角色后，若其他有效角色仍包含相同菜单，则该菜单继续有效。
- `granted_by` 只记录历史授权操作人，不决定该角色未来是否有效。管理员任命被撤销，也不自动撤销其以前合法授予其他用户的角色。
- 授权与回收操作均须保证授权关系、业务来源记录和审计的一致性，并联动 M6 实时更新权限状态。

**4. 可授权角色清单维护**

上级管理员可在自身管理权限范围内配置下级管理员能够授予的角色集合。配置时校验双方管理员等级、管理范围、角色类型及上级自身可委派的角色资格。

清单变更后立即影响下级管理员后续的角色分配和回收资格，但不自动撤销该管理员以前合法授予其他用户的角色关系。

可授权角色清单属于管理员操作约束，不属于 RBAC0 的角色继承关系；已由 `sys_admin_delegable_role` 表及 `sys_admin.delegable_revision` 修订号落实。

### 6.4 批量授权处理（4.4）

- **处理范围**：支持 2000 人以上的批量角色授权和回收。
- **预检查**：对请求去重，检查用户与角色有效性、操作人管理范围、可授权角色清单及输入一致性。每个目标都必须满足相应授权规则。
- **执行方式**：按可恢复的事务批次处理，记录各项成功、失败及处理状态。已提交的授权变更及时更新 M6 可信权限状态。
- **异常处理**：部分失败时返回成功数、失败数及失败对象和原因。重试仅处理尚未成功的事项，防止重复执行；不把跨多个事务的操作描述为整体原子成功。

### 6.5 OA 审批结果处理（4.5）

OA 负责审批，本系统不实现审批流程，只接收并执行可信 OA 系统已批准的授权或回收结果。

**处理步骤**：

1. 验证 OA 服务身份及其被授予的执行权限，确认事件来自可信 OA 系统。
2. 校验审批状态、唯一事件 ID、操作类型、目标用户、目标角色及审批内容完整性。
3. 根据 OA 服务的受控执行权限，检查操作是否在其允许的角色和对象范围内；不得将 OA 服务身份视为不受限制的超级管理员。
4. 校验目标账号、角色及当前授权状态，由 M4 执行批准的授权或回收操作。
5. 记录审批来源、事件编号、批准的操作内容、实际执行结果及审计证据，并通知 M6 更新可信权限状态。
6. 重复事件返回已记录结果；相同事件 ID 对应不同内容时拒绝执行并记录异常。

**执行主体规则**：

- 已批准的 OA 事件以**可信 OA 服务的受控权限**执行，不要求原申请人在事件执行时仍具有管理员资格。
- 原申请人后续离职或管理资格被撤销，不自动取消此前已经有效批准的事件。
- OA 只能执行经审批明确批准、且处于服务授权范围内的操作，不得自行扩大目标用户、角色或操作内容。
- OA 回收事件必须唯一定位 OA 审批产生的授权依据（以审批单号或授权依据标识对应）；撤销该依据时，若同一用户—角色关系仍存在其他合法授权依据则保留，不误删岗位来源或管理员手工授予的授权。
- OA 事件同样遵守超级角色保护、授权来源记录、数据完整性及实时撤权要求。

### 6.6 RBAC0 授权原则

M4 维护用户—角色关系 `UA` 和角色—菜单关系 `PA`，不直接为用户授予菜单或 API。

设 `UA(u)` 为用户当前有效角色集合，`PA(r)` 为角色当前有效菜单集合，则用户的有效菜单集合为：

\[
P(u)=\bigcup_{r\in UA(u)}PA(r)
\]

其中，有效角色和菜单必须满足启用状态、必要签名与版本要求，且菜单本身及其祖先目录均有效。

**授权规则**：

- 用户拥有多个角色时，权限取并集，不存在显式拒绝或角色继承。
- 角色停用、授权依据全部失效或角色菜单关系撤销后，相应授权不再参与计算。
- 管理员等级、可授权角色清单只约束授权管理操作，不自动给管理员增加业务菜单权限。
- M4 负责维护授权事实；JWT 校验、部门冻结检查、API 路由匹配及最终访问允许/拒绝由 M6 在线权限鉴定统一处理。

## 7. M5 管理员与管理范围控制

负责管理员任命、撤销、等级管理、组织管理范围判定、管理操作合法性检查及超级用户兜底。管理员等级用于限定管理资格和组织范围，不构成 RBAC1 角色继承关系。

管理员执行操作必须同时满足 **M6 的 RBAC0 功能权限要求** 和 **M5 的管理员资格、等级及适用管理范围要求**。

### 7.1 管理员任命与撤销（5.1）

- **任命**：具有管理员任命功能权限的有效管理员，可在自身管理范围及等级规则允许的条件下任命同级或下级管理员，不得越级任命或扩大自身管理范围。
- **撤销**：撤销操作需校验操作者功能权限、有效任命、管理等级及目标管理员所属管理范围。
- **同级互撤**：允许相同管理根部门、相同管理等级的管理员相互撤销任命，不允许仅因属于同一等级或同一上级部门就跨管理范围互撤。
- **自撤**：允许管理员撤销自己的管理员任命，撤销成功后立即失去相应管理资格。
- **历史保留**：撤销管理员任命只改变 `sys_admin` 中的有效状态，不删除该管理员此前合法授予其他用户的角色关系和历史审计记录。
- **实时生效**：管理员任命及撤销均须更新 M6 可信鉴权状态，防止已撤销管理员继续执行管理操作。

### 7.2 管理员等级管理（5.2）

管理员采用集团组织分级管理，数字越小表示管理等级越高。

| 管理等级 | 管理员类型 | 管理范围 |
|---|---|---|
| 一级（`admin_level=1`） | 总公司管理员 | 集团管理范围 |
| 二级（`admin_level=2`） | 分公司管理员 | 所属分公司及下属部门 |
| 二级（`admin_level=2`） | 总公司直属部门管理员 | 所属直属部门及下属组织 |
| 三级（`admin_level=3`） | 分公司或总公司直属部门的下级管理员 | 被任命部门及下属组织 |
| 四级及以下 | 更下级部门管理员 | 对应管理根部门及下属组织 |

**等级规则**：

- 管理员等级与组织管理层级对应，但不要求严格等于组织树深度，具体以有效任命记录为准。
- 任命管理员时，被任命者的管理范围不得超出任命者范围，且管理等级不得高于任命者。
- 同级管理员只有在符合管理范围和任命规则时才能执行相应管理操作，同级不意味着具有跨部门管理资格。
- 管理员等级不会自动赋予普通业务角色或菜单权限，实际管理功能仍需通过 M6 校验。
- 超级用户属于独立的系统兜底身份，不作为普通组织管理员等级参与日常分级管理。

### 7.3 管理范围判定（5.3）

M5 根据管理员的有效任命、管理等级、部门范围及可授权角色清单，确定其能够管理的对象和执行的操作。管理员等级不自动产生 RBAC0 功能权限。

- **集团管理范围**：一级总公司管理员具有集团范围内的组织和人员管理资格，可在具备对应功能权限时执行跨分公司管理操作。
- **部门管理范围**：二级及以下管理员以其有效任命中的 `sys_admin.dept_id` 为管理根，管理该部门及其下属组织。总公司直属部门管理员与分公司管理员均为二级，但不能因此跨部门管理。
- **全局资源管理**：应用、菜单、API、菜单—API 关联，以及全局角色定义和角色—菜单关系，均由具有对应功能权限的一级总公司管理员维护。二级及以下管理员不得修改这些全局配置。
- **用户角色授权范围**：管理员只能向自身管理范围内的用户授予或回收可授权角色清单中的角色。角色类型同时作为基础安全限制，普通管理接口不得分配超级角色。
- **可授权角色清单管理**：上级管理员可在自身管理权限范围内配置下级管理员的可授权角色清单。委派的角色必须属于上级自身有资格委派的集合，且不得违反管理员等级和管理范围限制。清单变更影响后续授权资格，不自动撤销历史合法授权。
- **管理角色限制**：分配管理功能角色不能自动建立管理员任命。管理角色的授权还须符合等级及可委派角色规则；执行管理操作仍需具有有效 M5 任命。
- **自我授权与回收**：管理员可以向自己授予或回收有权管理的角色，但自身必须属于其有效管理范围，且拟操作角色位于当前可授权清单内，不得借此绕过等级、范围及超级角色限制。
- **数据访问控制**：管理列表按实际管理范围过滤；详情、修改和批量操作须对每个目标重新检查，不能仅依靠前端隐藏或客户端提交的对象 ID 判断权限。
- **组织变化处理**：部门合并、撤销或层级调整后重新校验管理范围。若原任命范围失效或发生未经批准的扩大，先限制受影响管理操作，再由有资格的管理员重新审核任命，不自动扩大管理权限。

### 7.4 管理操作合法性检查（5.4）

管理后台请求执行前，必须通过 **M6 功能权限校验** 和 **M5 管理资格及范围校验**。M5 根据操作类型检查适用条件，而非所有管理请求均执行相同的部门范围检查。

| 校验内容 | 责任模块 | 判定要求 |
|---|---|---|
| 身份与会话 | M6 | JWT 有效、账号可用、会话未失效，且不受禁止管理操作的部门冻结限制 |
| 管理功能权限 | M6 | 当前有效角色具备对应管理菜单及 API 权限 |
| 管理员任命 | M5 | 存在当前有效的管理员任命 |
| 管理等级 | M5 | 操作符合管理员等级规则，不得越级任命或扩大管理范围 |
| 对象管理范围 | M5 | 目标用户、部门或管理员处于操作者有效管理范围内 |
| 可授权角色范围 | M5 | 拟授予或回收的角色属于操作者当前可授权角色清单，并符合角色类型限制 |
| 上级角色委派 | M5 | 委派对象符合上下级关系，委派角色不超出上级自身可委派范围 |
| 全局资源管理资格 | M5 | 修改全局资源、角色定义或角色—菜单关系时，须为有效一级总公司管理员 |
| 数据及变更安全 | 对应业务模块及公共支撑 | 数据签名、授权来源、并发版本和可信状态满足要求 |

**按操作类型执行校验**：

1. **用户角色授权与回收**：检查功能权限、管理员资格、目标用户范围及角色可授权资格。对自己执行授权或回收时采用同样规则，不因操作者与目标用户相同而跳过检查。
2. **管理员任命与撤销**：检查功能权限、管理等级及目标部门范围。允许符合规则的同管理根、同等级管理员互撤和管理员自撤，不允许越级或跨范围操作。
3. **全局资源与角色配置**：检查对应功能权限和有效一级总公司管理员资格，由 M3 或 M4 执行资源及角色配置变更，不要求具有部门对象的操作进行无关的部门范围检查。
4. **可授权角色清单配置**：检查上下级管理员关系、双方管理范围及角色委派资格。下级获得的可授权角色集合不得超出上级能够合法委派的集合。
5. **其他人员与组织管理**：依据实际操作类型检查目标用户或部门范围，再由对应业务模块执行。

**执行与异常规则**：

- 管理后台先由 M6 检查功能权限，再由 M5 校验管理员资格及实际对象范围；全部通过后，交由 M1—M5 中对应的业务模块执行。
- M6 的 API 鉴权只判断功能权限，不能替代 M5 对 `userId`、`deptId`、`roleId` 等实际业务对象及角色资格的检查。
- 涉及授权或任命的修改须在提交前确保操作者资格、目标范围和可授权清单仍有效，使用事务及版本控制防止并发越权。
- 用户—角色回收还须由 M4 核实具体授权依据，不能因某管理员有权管理该角色就错误删除其他独立合法授权来源。
- 检查失败时拒绝操作，防止泄露范围外对象信息，并记录必要审计；权限变更后通知 M6 更新可信状态。

**OA 审批结果的特殊处理**：可信 OA 事件由 M4 按 OA 服务已获批准的操作、目标对象和角色范围执行，不要求 OA 服务具备普通管理员任命，也不重新依赖原申请人的当前管理员资格。但必须验证 OA 服务身份、审批结果及其受控执行范围，不允许通过 OA 绕过超级角色保护或扩大审批内容。

### 7.5 管理权限撤销处理（5.5）

- 撤销管理员任命后，该用户立即失去对应管理资格，即使因其他角色仍能看到管理菜单，也不得继续执行要求管理员身份的操作。
- 管理员任命与角色授权分别管理，撤销任命不自动回收本人的全部管理功能角色，也不撤销其此前授予其他用户的合法角色。
- 管理界面可根据当前任命资格隐藏不可操作的管理功能，但前端隐藏不能替代后端 M5 校验。
- 保留管理员任命、撤销及历史授权记录，确保管理行为可追溯。
- 所有撤销操作均须通过可信状态更新，确保后续管理请求无法继续使用已失效的管理员资格。

### 7.6 超级用户初始化与兜底（5.6）

- **系统初始化**：通过受控初始化流程创建超级账号、超级角色及必要的用户—角色关系，同时登记统一权限管理系统自身的菜单和 API，确保系统具备管理自身资源与权限的能力。
- **权限覆盖**：超级角色须覆盖所有已登记且可授权的有效菜单，包括本系统及各接入业务系统。新增菜单时通过受控资源登记流程同步维护超级角色授权，不仅依赖账号或角色类型字段。
- **使用限制**：超级用户仅用于初始化、紧急管理和权限恢复，不承担日常资源维护工作；正常资源管理由一级总公司管理员完成。
- **恢复保障**：普通管理员权限误撤或关键管理角色失效时，保留受控的超级用户恢复通道；恢复操作应验证管理员身份并完整记录审计。
- **安全要求**：超级用户凭据须独立保护，禁止通过普通管理接口随意创建超级用户或超级角色。发生签名篡改、数据完整性故障时，应先保全现场并执行安全恢复流程，不得以超级用户身份直接绕过验签失败放行。

## 8. M6 在线权限鉴定

M6 负责身份及当前状态检查、有效菜单计算、菜单权限查询、后端 API 鉴权、权限变更实时生效和高性能鉴权状态访问。
M6 只读取和判定当前权限，不直接修改用户—角色、角色—菜单等业务授权关系。授权数据由 M1—M5 维护，变更后的可信状态由 M6 统一协调。

### 8.1 身份与状态有效性检查（6.1）

- **服务身份校验**：验证接入业务服务的可信身份，确认其绑定的应用 `appCode`，不直接信任客户端提供的应用标识。
- **JWT 校验**：检查签名、签发方、受众、有效期及会话失效状态，以 JWT 中经过验证的用户标识确定请求主体。
- **账号检查**：读取当前账号状态。账号暂停、离职或必要身份数据验签失败时，拒绝受保护业务访问。
- **部门冻结检查**：检查用户所属部门及其祖先部门，任一部门被冻结时，拒绝业务权限鉴定。
- **数据可信检查**：使用通过数字签名及版本校验的账号、组织和权限数据，不使用不可信或过期状态作为放行依据。

**登录与鉴权区别**：部门冻结允许用户通过 M1 正常登录、注销和进行必要的密码安全操作，但不能使用受保护的业务功能。JWT 有效不代表当前业务权限有效。

### 8.2 有效菜单权限计算（6.2）

根据 M4 维护的当前有效用户—角色关系、角色—菜单关系，以及 M3 提供的资源状态，计算用户的有效菜单集合。

**计算规则**：

1. 获取用户当前有效角色。只有仍存在合法授权依据且角色处于启用状态的用户—角色关系才能参与计算。
2. 汇总各有效角色拥有的权限菜单，取并集并去重。
3. 过滤停用菜单、所属应用已停用的菜单，以及存在停用祖先目录的菜单。
4. 校验必要授权关系和资源数据的签名及版本，排除不可信数据。
5. 返回指定应用下的有效权限菜单集合。

**权限原则**：

- 多角色菜单权限取并集，不存在角色继承和显式拒绝权限。
- 同一用户—角色关系存在多个授权依据时，由 M4 保证其有效性；撤销其中一个依据不必然使角色失效。
- 目录仅用于导航，不产生额外菜单授权；但停用目录会使其下级菜单失去有效性。
- 管理员等级及可授权角色清单不自动增加用户的业务菜单权限。

计算结果允许保存为带版本的可信权限快照，但每次使用前必须确认其未过期于当前可信权限版本。

### 8.3 菜单权限查询（6.3）

- **输入**：当前有效 JWT、指定应用标识。
- **处理**：验证用户身份、账号和部门状态，依据 8.2 节计算指定应用的当前有效菜单。
- **输出**：返回可用权限菜单及必要的祖先导航目录。补全目录只用于展示，不产生新的授权。
- **冻结处理**：账号可用但部门被冻结时，返回空的业务菜单集合；用户仍可使用必要的账号安全功能。
- **异常处理**：JWT 无效或已过期返回 401；账号暂停、离职等状态拒绝访问；可信权限数据不可用时返回服务不可用，不使用旧权限结果替代。

前端根据菜单结果控制功能入口的显示或灰显，但所有受保护 API 仍须独立经过 M6 鉴权。

### 8.4 后端 API 权限判定（6.4）

M6 根据可信业务服务身份、实际请求 API 和用户当前有效权限，返回允许或拒绝的鉴权结果。

**处理步骤**：

1. 验证调用服务身份，取得可信应用 `appCode`。
2. 校验 JWT、当前会话及账号状态。
3. 检查用户所属部门及祖先部门是否冻结。
4. 使用可信业务服务端识别的实际路由模板和 HTTP 方法，匹配 M3 已登记的 API；未知、歧义、已停用或所属应用不一致时拒绝。
5. 获取当前可信授权版本及相关权限状态；存在拒绝栅栏、版本不一致、必要签名无效或状态不可信时，不得放行。
6. 检查用户是否拥有至少一个有效权限菜单，且该菜单与目标 API 存在有效关联。
7. 生成允许或拒绝结果，附决策标识和必要依据，交由可靠审计机制记录。
8. 将结果返回业务服务端，只有明确 `allowed=true` 时才允许执行受保护操作。

**判定规则**：

- 应用、API、菜单及其祖先目录均须符合当前有效性要求。
- 同一 API 关联多个菜单时，拥有任一有效关联菜单即可满足菜单授权条件。
- 不得依赖前端传入的用户 ID 或自行声明的路由模板决定授权。
- 管理后台 API 也须通过 M6 功能鉴权，但涉及实际用户、部门或角色对象的管理请求，还须由业务处理入口执行 M5 管理资格和范围检查。

### 8.5 权限变更实时生效（6.5）

**目标**：权限撤销操作成功完成后，后续开始的相关 API 鉴权不得继续依据已撤销权限错误放行。若其他合法授权仍提供相同权限，更新完成后应按 RBAC0 并集规则正常允许。

**1. 权限缩减处理**

对角色回收、角色停用、菜单或 API 停用、部门冻结、账号离职等可能缩减有效权限的操作，采用以下流程：

1. **确定影响范围**：识别受影响的用户、角色、菜单、应用或组织子树。
2. **建立拒绝栅栏**：在所有鉴权实例共同依赖的可信状态中标记受影响范围，确认保护生效后才允许修改权限事实。
3. **提交业务变更**：由对应业务模块在数据库事务内更新授权或资源状态，同时保存必要签名、变更记录和关键审计证据。
4. **更新可信权限**：根据提交后的权威数据重新计算并验签相关权限，生成新版本可信权限快照。
5. **解除栅栏**：确认新版本已经可靠发布且所有鉴权实例能够识别最新状态后，解除临时限制并报告变更成功。

栅栏只用于权限变更期间的安全保护，不作为 RBAC0 中的显式拒绝权限，也不永久撤销其他合法授权。

**2. 权限扩大处理**

新增角色授权、增加角色菜单、重新启用资源及解除部门冻结等操作，在业务数据完成提交、签名校验和可信权限版本更新后才开放新增权限。

权限扩大不必普遍设置拒绝栅栏，但必须保证新授权不会在可信数据确认前生效。

**3. 并发与失败处理**

- 以撤权操作成功返回作为生效边界：此后开始的相关鉴权必须使用新状态或安全拒绝。
- 已经通过鉴权并开始执行的业务操作，不在本期通过 M6 自动撤销。
- 数据库提交成功但缓存或权限版本发布失败时，保持受影响范围的安全限制，记录待恢复状态，不虚报成功或回滚。
- 变更未提交时，必须在核实权威数据和原有可信状态后，才能安全解除栅栏。
- 拒绝栅栏不能仅因超时自动解除；恢复须验证实际授权状态。
- 并发权限变更须通过事务、版本或等效协调机制避免相互覆盖或错误解除栅栏。

**4. 状态持久化**

权限版本、变更状态及拒绝栅栏须具有可靠的权威存储，并能在服务重启后恢复。所有鉴权实例在返回允许前必须核对可信版本与栅栏状态，不能只相信本地保存的旧权限快照。

数据库和共享缓存之间不默认具有原子事务，因此实际存储方式、发布顺序及故障恢复流程须由后端与数据库设计共同落实，并通过并发测试验证。

### 8.6 高性能鉴权状态访问（6.6）

**1. 可信权限缓存**

- MySQL 保存账号、组织、资源及授权关系等权威业务数据。
- 常规鉴权优先读取已验签、带版本的可信权限快照，避免每次执行多次数据库关联查询。
- 受保护数据的数字签名主要在快照建立和更新时验证；在线鉴权仍须核对当前可信版本及变更状态。
- 可选择 Redis 等共享缓存技术，但不强制指定具体产品。
- 不允许使用未经可信版本校验的长期本地允许缓存。

**2. 缓存故障处理**

| 情况 | 处理规则 |
|---|---|
| 缓存正常且版本可信 | 正常进行权限判定 |
| 缓存缺失或数据过期 | 从可信数据源重新构建，验证通过后使用 |
| 缓存不可用但可安全回源 | 在能够确认最新授权版本、拒绝栅栏及数据完整性的前提下进行数据库鉴权 |
| 无法确认当前可信状态 | 拒绝放行，返回服务不可用 |
| 关键签名无效 | 拒绝使用对应数据，记录异常并保留证据 |

故障降级不得绕过权限版本与撤权状态检查，不能使用旧缓存默认允许请求。

**3. 鉴权审计**

- 每次鉴权记录用户、应用、API、决策结果、权限版本、时间及必要的授权依据摘要。
- 对允许请求，应能够追溯当时起作用的用户—角色、角色—菜单及菜单—API 关系，而不是使用后来的权限状态反推。
- 关键授权变更须可靠保存审计证据；高频鉴权日志可以通过持久化审计队列异步落库，以减少在线延迟。
- 若必需审计证据无法可靠接收或保全，不得静默丢弃；按安全策略拒绝或返回服务不可用。
- 审计记录不得泄露密码、验证码、完整 JWT 或敏感个人信息。

**4. 性能与安全验证**

- **性能目标**：正常鉴权耗时目标不超过 20ms，上限 50ms；实际统计口径由测试规范明确。
- **登录负载**：验证约一万人早高峰集中登录下的身份认证及权限服务表现。
- **撤权测试**：模拟角色回收、部门冻结及资源停用与 API 请求并发发生的场景，要求撤权成功完成后的错误放行次数为零。
- **异常测试**：验证缓存失联、版本冲突、签名失效、服务重启、审计故障及数据库恢复时的安全行为。
- **性能记录**：分别统计 JWT 校验、权限查询、版本核对、审计接收和请求总耗时，避免仅使用平均耗时判断性能达标。

上述性能指标属于设计目标，必须经过实际测试。

## 9. 公共支撑与数据安全

### 9.1 敏感数据与凭据保护

姓名、手机号采用 AES-GCM 加密，手机号以独立密钥计算 HMAC-SHA256 索引；密码以带盐 scrypt 哈希存储。短信验证码按用途隔离、限时限次、一次性核销，不保存可直接使用的明文验证码。接口按管理范围展示必要信息，手机号脱敏；日志禁止写入明文密码、验证码、完整 JWT 和密钥。

**密码策略**（适用于首次设密、修改密码和重置密码，与 3.5 节流程配套）：

| 项 | 规则 |
|---|---|
| 长度 | 8—64 个字符 |
| 复杂度 | 至少包含字母和数字两类字符，允许但不强制特殊字符 |
| 弱口令限制 | 不得包含用户名、姓名拼音或完整手机号 |
| 历史限制 | 不得与该账号最近 5 次使用过的密码相同 |
| 锁定策略 | 连续 5 次验证失败锁定 15 分钟，锁定期间拒绝密码校验 |
| 有效期 | 本期不强制定期更换，仅强制首次设密和找回重置 |

加密密钥、HMAC 密钥、JWT 签名密钥与数据签名密钥应分开管理，明确存储位置、访问权限、轮换和恢复办法。

### 9.2 数据签名与完整性

沿用 `sys_data_signature` 的 Ed25519 签名机制，保护影响身份、组织、授权及管理资格判断的数据；新增的授权来源、可授权角色清单等关键记录也应纳入完整性保护。签名与业务变更须保持一致，验签失败时隔离相关不可信数据并留存证据，不自行重签放行。

统一签名字段顺序、编码、空值、时间序列化及密钥标识。现有 `sign_version` 表示签名数据格式版本，不能直接当作密钥 ID；数据库设计已在 `sys_data_signature` 补充 `key_id` 字段标识签名密钥，支持轮换。已验签结果可随可信版本缓存。

### 9.3 审计与历史证据

`sys_login_log` 记录认证结果，`sys_operation_log` 记录管理操作、HR/OA 事件及鉴权结果。审计关联 `requestId`、`decisionId`、操作主体、时间、结果、权限版本和**当时**的授权依据；业务执行结果由业务系统使用相同请求标识关联，不以当前角色关系倒推历史权限。

日志永久保留且普通业务不可修改。关键变更的审计证据应与业务事务可靠关联；高频鉴权日志可在**可靠持久接收后**异步写入。日志哈希链等强化措施为可选实现，不作为本期必建子系统。

### 9.4 备份与人工恢复

执行每周全量、每日增量备份并定期验证可恢复性。发现篡改时先保全现场、隔离受影响数据；由授权人员人工恢复。恢复后重新验签、重建权限版本和可信缓存、记录恢复审计，确认可信后再开放相应服务。

## 10. 事务、异常与内部处理约定

### 10.1 事务及跨模块一致性

| 场景 | 提交边界与异常处理 |
|---|---|
| HR/OA 事件 | 事件幂等记录与本次业务结果可靠关联；重复事件返回已有状态，同号不同内容拒绝 |
| 角色及授权来源变更 | 授权依据、有效用户—角色关系、签名和关键审计协调提交；不能误删其他有效依据 |
| 资源、角色菜单及管理员变更 | 事务内保存业务事实及变更记录；权限缩减先建立保护，可信状态发布后才确认完成 |
| 调岗及部门合并 | 调岗分阶段留痕；合并确保组织树与人员归属一致，原角色关系按既定规则保留 |
| 批量授权 | 分批提交并逐项记录结果；失败项幂等重试，不默认回滚其他已完成批次 |

MySQL 事务只保证本地数据提交，不自动保证数据库与缓存原子一致。跨系统发布失败时记录待恢复状态，按第 8.5 节处理，不将“已提交”误报为“全部生效”。

### 10.2 统一异常响应

| 场景 | 接口处理原则 |
|---|---|
| 请求参数非法 | `400`，返回字段错误，不泄露敏感数据 |
| 身份凭据或 JWT 无效 | `401`；登录失败提示不区分账号是否存在 |
| 有效身份但无功能权限、管理范围或角色资格 | `403`；范围外对象可按统一反枚举策略返回 `404` |
| 重复事件内容冲突、并发版本冲突 | `409`；处理中事件返回明确的处理中状态，不重复执行 |
| 签名、版本或权威权限状态暂不可用 | 安全拒绝，必要时返回 `503`，禁止降级放行 |

部门冻结用户可以登录，业务菜单查询返回空集，受保护业务 API 拒绝；接口必须区分“鉴权拒绝”和“服务故障”。具体错误码及响应体由 API 规范统一。

### 10.3 内部处理接口

| 逻辑接口 | 调用目的及主要结果 | 主责 |
|---|---|---|
| `校验管理操作` | 校验功能权限、管理员范围及可授权角色资格，返回判定依据 | M6、M5 |
| `处理外部事件` | 核验来源、事件号及版本，返回可重放处理状态 | M2、M4 |
| `提交授权变更` | 修改授权事实及来源，返回影响范围与提交结果 | M4 |
| `协调可信状态发布` | 执行受控变更、版本发布与失败恢复协调 | M6 |
| `验签读取` / `记录审计` | 返回可信事实或持久审计接收结果 | 公共支撑 |

上述为**模块间逻辑契约**，不是对外 HTTP 接口；请求参数、响应结构和错误码在 API 设计中进一步定义。

## 11. 数据库适配与必要修改建议

数据库设计 v3.0 共 22 张表（13 张业务表 + 9 张支撑表），继续作为 RBAC0 核心数据基础，不新增直接“用户—菜单”授权关系，也不提前建立 RBAC1 角色继承表。以下**最小逻辑数据支持**已由 9 张新增支撑表及既有表字段调整落实（授权依据 `sys_user_role_source`、可授权清单 `sys_admin_delegable_role`、外部事件 `sys_external_event`、权限版本 `sys_permission_revision`、撤权栅栏 `sys_deny_fence`、短信验证码 `sys_sms_code`、会话失效 `sys_session_invalidation`、密码历史 `sys_password_history`、服务身份 `sys_service_identity`）：

| 数据缺口 | 建议适配 | 对应需求 |
|---|---|---|
| 人员标识与首次设密 | `sys_user` 以 SG 号作为稳定人员标识（确认映射至 `employee_no`）；增加密码初始化标识，未设密使用不可登录的随机占位哈希 | 一人一号、首次设密、密码重置 |
| 多重授权来源 | 增加用户—角色授权依据记录：用户、角色、来源类型、来源标识、来源部门/岗位、状态；有其他有效依据时保留 `sys_user_role` | 调岗精确回收、OA 与岗位授权并存 |
| 可授权角色清单 | 记录管理员与可委派角色的关系及变更来源，支持上下级委派校验 | M4 授权范围、M5 分级管理 |
| HR/OA 事件及阶段结果 | 建立唯一 `(source_system, event_id)` 的事件处理记录，保存载荷摘要、业务版本、处理状态；调岗另记录阶段进度 | 幂等、乱序拦截、失败恢复 |
| 可信权限变更状态 | 持久记录权限版本、受影响范围、拒绝栅栏及发布状态；缓存只保存可核验的可信快照 | 实时撤权、重启恢复 |
| 可信服务及会话 | 维护业务/OA 服务身份与应用、操作范围的可信绑定；补足验证码一次性状态与会话失效数据 | 服务认证、验证码核销、注销与密码重置 |
| 签名及并发控制 | 为必要签名增加密钥标识；补足角色菜单等并发版本，新增关键授权数据纳入签名范围 | 完整性与并发更新 |

**约束**：SG 号与用户名生成规则以第 3.1 节为准；部门以 `sys_dept.id` 唯一识别，HR 外部标识不同时须确定映射。手机号仍须唯一，临时账号允许无工号但必须绑定手机号。上述新表已在建表 SQL 中定义唯一键、索引及历史保留触发器；事务边界与迁移办法在实现阶段继续执行。

## 12. 性能验证与实施检查

| 验证项 | 重点检查 |
|---|---|
| 登录高峰 | 模拟约 10,000 人集中登录，分别测试账号密码、手机号密码两种方式及限流；记录成功率、吞吐和响应时间 |
| 在线鉴权 | 统计端到端耗时与 P50/P95/P99/最大值，核对原需求 **20ms 目标、50ms 上限**；不擅自改写为特定分位数承诺 |
| 实时撤权 | 并发撤权与请求、版本发布失败、服务重启；成功返回后发起的相关鉴权错误放行数为 0 |
| 权限规则 | 验证多重授权依据、可授权角色清单、自我授权、OA 受控执行、目录级联停用、部门冻结及管理范围 |
| 批量及外部事件 | 2000 人以上批量授权、重复/乱序 HR/OA 事件、部分失败与恢复 |
| 安全与故障 | 签名篡改、缓存/审计不可用、伪造服务身份、未知 API、密码重置与旧会话失效 |

**数据准备**：样本约含 10,000 名员工、111 个部门、18 个应用及 359 个功能点。导入时按 SG 标识关联人员、按确认的部门 ID 映射建树；生成登录名使用拼音首字母，重名追加 SG 后六位。功能点清单不能替代真实 API 路由登记。演示配置至少两个业务系统（各 3—4 个菜单），同时覆盖本系统菜单/API 与受控超级用户初始化。

**设计交付核对**：模块处理说明与数据流、数据字典、关键判定表、接口契约和测试用例一致；必要图件可独立提供，但正文不依赖图片才能理解。上述指标均为待验证目标，不视为已通过测试。
